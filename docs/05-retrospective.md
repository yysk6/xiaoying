# 项目复盘与下一步

## 最难的问题：让“完成”有真实含义

这次项目最需要解决的，是模型说完成、流程走到最后和业务真实完成之间的差别。只按顺序调用检索、脚本、估算、保存，无法证明Agent会根据反馈调整；模型写出8，也不能证明预算正确或方案已经提交。

我的处理思路是先把验收转成可核对的事实：预算由程序逐项相加；脚本和估算绑定候选输入/版本；SQLite提交才完成；失败attempt单独保留；未来活动保持planned。然后要求真实模型运行“先看到12超预算，再改成8、重估、保存”的路径，而非用从一开始直接选8代替重规划。

结果见[E04观察与动作](../examples/live/core20/20261031T110356Z-93ca1d21/E04/observations.json)：模型确实收到12、缺口2与可行替代8，之后修订、重估和保存；素材和脚本保留。这是本次最有价值的验证链路。

## 失败后如何保留成果

仅加自动重试会隐藏决策，也可能重复执行已经成功的工作。本项目把错误作为下一次模型观察；模型决定重试或停止，程序限定重试次数并保持成功产物。

[E17](../examples/live/core20/20261031T110356Z-93ca1d21/E17/trace.jsonl)通过实际SQLite触发器制造保存失败，失败时plan0；模型观察SAVE_FAILED后重试，最终只提交1份plan，原失败仍在。E15脚本首次失败后恢复，E16持续失败则诚实未完成；E18显式续跑保留成功前缀。这让我更清楚：checkpoint解决恢复位置，业务仍需处理事务、幂等、产物有效性和累计额度。

强杀进程后的一个离线恢复测试首次出现CHECKPOINT_NOT_FOUND；针对性复测及最新完整408项均通过。当前执行结论是复测成功，历史异常留档，未声称进行了根因修复。需要继续观察该崩溃边界，不能把一次通过解释为任何故障下都可靠。

## 我对AI开发方式的调整

项目初期，我要求先调研、写规格，再分阶段实现和验收，避免让AI一次性生成难以检查的大量代码。随后我也发现流程被执行得过细：缺模块/方法被拆成多轮、证据重复、审查结束前过早做安装验证、多个文档反复维护相同状态。

我明确反馈这些工作耗时过长，并要求AI总结原因、调整开发规则。后续保留必要的规格、行为测试和审查，收敛辅助材料与重复验证。这个过程的收获是：会使用AI不仅是给出详细提示，也要判断哪些过程真的降低风险，及时停止不创造业务价值的工作。对应记录见[开发约定](../AGENTS.md#development-workflow)。

讨论记忆与DeepAgents时，我先要求解释收益和与现有设计的关系，再回到单任务、有限工具和明确验收，最终保留轻量LangGraph。框架提供可用能力，但不能替代对业务边界的判断。

## 评测器本身也可能错

CORE20的检查器最初能对被删掉步骤、被改数据库预算、被清空成功结果观察的证据给出通过。审查通过三个反例复现后，补齐步骤全集、持久输入关联和每轮观察的独立重建，再做Green验证。

另一次保存失败场景的检查器误报来自“实际失败ToolResult没有state_patch”；补足事件事实重建后才正确核验模型收到的SAVE_FAILED。这里学到的是：业务系统的输出不能自己证明自己，评测器也不能只看最后JSON或用同一个计算函数生成预期。

## 实际效果与产品体验

当前核心20/20、离线408/408通过，但仍存在可解释的局限：E07/E08各有一次多动作协议错误后纠正；E16多申请一次已达上限的脚本请求，随后停止。最终状态正确，不等于路径最短。

我亲自试用自然语言CLI后发现，“你好”仍得到字段待补模板。这使我区分了字段抽取与自然对话Agent：当前入口可以整理、修改并确认需求，尚不能围绕正在运行的任务自由交流。后续改进应从意图识别和任务状态事实入手，而非仅把固定模板换成更长的回复。

## 其他实际技术收获

| 观察到的问题 | 处理与验证 |
|---|---|
| Pydantic运行校验拒绝非法值，导出Schema却丢pattern | 改用字段校验与内部类型注解，测试Schema与运行语义一致，见[领域/契约测试](../tests/unit/test_contracts.py) |
| 日期解析会规范化非法偏移分钟 | 明确拒绝无效偏移；严格整数拒绝bool/float，期限缺口用整数向上取整覆盖微秒，见[领域测试](../tests/unit/test_domain.py) |
| 同次当前/替代报价分别读Clock造成比较偏移 | 一个估算共享同一时刻，下一次显式估算再取时，递增Clock反例验证 |
| 只冻结Catalog外层仍可改内部素材 | 本地工具隔离已验证资料快照，避免文件哈希与实际使用内容偏离，见[工具测试](../tests/unit/test_tools.py) |
| Literal[True]接受数字1/1.0 | 加严格布尔校验，真实加载Red/Green确认，见[资料测试](../tests/unit/test_catalog.py) |
| 保存/模型已落盘但checkpoint滞后时重复执行 | 按operation/kind复用已持久响应与补丁，计划提交事实优先；未知结果独立interrupted/新尝试，见[恢复测试](../tests/acceptance/test_resume.py) |

这些是实际实现中学到的具体边界，不能由采用框架自动获得。部分运行结果属于不同历史阶段，不把早期局部测试数量累加为当前用例数。

## 学习收获

- 动态决策要通过“观察→动作变化→实际结果”证明；固定流程和自动重试不足以证明模型效果。
- 类型、Schema、指纹和数据库事务能为模型提出的动作提供确定性边界。
- 记忆不仅是保存聊天，还包括有效产物、版本、约束、失败和剩余额度；上下文压缩应保留必要事实。
- AI产出需要需求、测试、审查和真实评测互相约束；数量更多的文档和测试，不必然意味着验证更有效。

## 下一步

1. 增强自然语言对话：参考 Codex、WorkBuddy 的交互体验，让用户能用自然语言咨询、补充或修改需求，并围绕当前任务询问进度、结果和后续操作。先明确意图识别、任务状态和确认边界，再实现对话。
2. 增强上下文压缩：在现有历史消息摘要和长度控制的基础上，完善长对话中的压缩与恢复，保留主题、预算、截止时间、用户确认、任务状态和关键工具结果，减少对话增长带来的上下文负担。
3. 提升路径效率：减少多动作协议错误和无效重试，用独立案例验证。
4. 扩大验证边界：在当前每例一次的基础上固定重复采样计划，补崩溃时序与Linux验证，分别报告结果。

以上均为下一步，尚未实施。本次没有完整统计个人开发工时，不把模型运行耗时或测试时间代替开发用时。当前结论见[评估](03-evaluation.md)。
