## 真实模型评估

至少执行 L01 正常、L02 工具失败、L03 预算受限三类场景。L01/L02 必须来自普通入口的完整 live 调用，不使用预制决策日志。每个场景建议运行3次，样本很小，只报告次数，不报告泛化成功率。

- L01：约束可行，检查真实调用参数、估算和最终提交；不强求模型选择premium。
- L02：检索成功后令脚本生成工具第一次返回可重试失败，模型必须观察后自己选择重试或说明未完成。仅由程序自动重试不算通过“动态调整”检查。
- L03：预算10。模型可能直接选择basic，这是合理行为，不能为了演示强迫它先犯错。若没有出现12->8轨迹，不写“已验证超预算后的模型重规划”。

若需要专门验证“观察12后调整”，增加 L04 **显式状态夹具**：测试setup使用真实本地工具建立premium候选与12-unit估算，记录origin=fixture_setup；不伪造模型消息、工具调用或决策理由。随后把该事实状态交给真实模型，让其选择修订/估算/保存或停止。它验证给定状态下的真实模型决策，不能标注为从空输入开始的完整live路径，也不能替代L01/L02。

Live断言按性质判断，不要求固定措辞/严格工具顺序：完成时约束与保存事实必须正确；无依据内容为失败；失败时保留结果且不虚报；响应工具观察的动作与理由可核查。工具改变前后对照使用新request_id，明确保留两边运行记录。

现有`scripts/evaluate_live.py`对L01/L03主要按completed判定；L02观察故障后completed或tool_failure均可标passed。它没有逐项独立核算预算、查询plan行数、检查产物复用或评判12→8，因此目前不足以作为题目全部审核点的最终评测器。

### 本轮案例与通过条件

第一批固定三个必需场景，各一个新样本。使用独立评测数据库、新request_id及当前时间+4小时deadline，保持原报价和提示版本；不改生产提示强迫模型先选premium。沿用L编号，避免覆盖S7历史目录。

| 场景 | 输入/控制条件 | 预期观察与判定 | 计划制定时状态 |
|---|---|---|---|
| L04：给定初始12后的重规划 | budget10；setup通过真实检索、脚本生成、修订和估算建立premium12，结果含basic8的替代报价；接着交给真实planner | 模型收到12/预算缺口2/替代8，自己修订为可行候选；当前候选重新估算8后保存一次；约束通过；同素材同brief只换档位时原脚本保留且不再次生成 | NOT_RUN；评测入口待实现 |
| L05：当前资料内无可行方案 | budget5；从普通完整live入口执行，最低basic8 | 真实估算或替代报价支持最低缺口3；模型通过stop_task明确constraints_unsatisfied；incomplete、saved_plan=null、plans行数0；不能放宽预算或声称全局无解 | NOT_RUN；评测入口待实现 |
| L02：一次失败后的恢复与保留 | 普通完整live入口；首次generate_script在HTTP前注入一次可重试错误，其余均真实 | 下一次planner确实收到失败；自主重试后完成；失败attempt仍failed，后续attempt单独succeeded；已成功检索和候选保留，检索实际执行仅一次；保存一行 | 历史一次恢复成功；本轮严格判定NOT_RUN |

L04中setup的每个动作与真实返回均记录origin=fixture_setup，脚本使用真实DeepSeek生成，12/8由本地实际报价计算。模型接手后使用正常循环、工具及SQLite；setup不写虚构assistant/tool消息，也不提供“下一步选basic”的指令。它证明题目给定初始方案后的真实决策，报告必须标明不是从空白输入自主产生premium方案的完整路径。计划制定时L04尚无可运行入口；现已实施的入口与实际执行证据见专项报告，不用历史L01—L03冒充。

L02若模型有依据地选择停止，记为“失败处理通过、恢复未达成”，不能混为“恢复成功”。一次重试与预算驱动的候选修订分别评价；只有L02通过不能宣称高分所需重规划已经验证。L05若因HTTP错误或调用上限停止，虽未违规保存，也不满足“根据约束主动停止并报告缺口”的行为目标。

可选L06在同一次任务串联L04重规划与一次保存失败：候选重新估算可行后，评测边界令首次真实保存事务提交前失败；后续由模型决定重试或停止。检查成功脚本/估算仍在、失败当时plan为0、恢复保存后plan为1。该组合用于补充同一任务同时重规划和恢复的证据，不属于第一批三个样本，不在本轮计划制定时实现或调用。

### 独立判定，不以completed代替审核

1. **预算与时间。** 检查器从本次锁定资料独立求和：premium=1+2+8+1=12、basic=1+2+4+1=8；预算10时缺口分别2/0，预算5时最低缺口3。核对四分项、合计、分钟、保存时刻与deadline；不能调用业务quote函数作为唯一预期来源。模拟units与API费用分别记录。
2. **依赖与失效。** 素材先检索再选择，脚本匹配当前素材/brief，估算匹配当前revision/script/pricing；换档位后旧estimate失效，保存引用新estimate。L04旧脚本可复用，不能把旧估算当新估算；错误引用应被拒绝且不写plan。离线边界测试验证拒绝路径，live检查实际选择遵守依赖。
3. **状态与保存。** 联查output、Trace和真实SQLite。completed须有且仅有一行对应plan；未完成须零行、saved_plan=null。首次失败永久保留failed及错误码；重试成功不覆盖它。报价工具成功但feasible=false是“估算成功、方案不可行”，不能误记为工具失败。task_plan的四项制作活动保持planned。
4. **观察导致决策。** 留下输入模型的必要事实安全投影（预算、当前报价、缺口、替代报价或最近失败及其事件引用），关联下一次真实模型调用、所选动作、公开rationale和工具结果。Trace关联ID单独不足以证明模型收到哪些事实；不导出完整上下文或内部推理。模型必须自己产生修订/重试/停止动作，调度器不代选或自动重试。
5. **保留有效成功结果。** 比较故障/修订前后的material_id、candidate/script指纹及实际调用次数。无失效原因的成功产物仍可用；换素材/brief则允许依法失效，不能以“保留结果”为由复用失效产物。
6. **内容事实性。** 独立人工核对脚本断言与所选素材facts，单列事实支持/待核实/无依据及原文位置。当前百分比/禁用语校验不能证明语义真实性；历史样本中的“一键”“几秒钟”“精准”等须逐条核对，链路完成不覆盖内容问题。

每例分别记录`invariants_pass`（计算/依赖/状态/保存）、`behavior_pass`（该场景目标决策）、`content_pass`及对应事件/产物引用；L02另记failure_handling与recovery结果。任一必需项失败则该例整体不通过；NOT_RUN和外部阻塞分别列出。正确的L05以incomplete通过评测，completed本身不是统一通过条件。评分只用上述门槛与逐项结论，不虚构题目未规定的分值或稳定性成功率。

## 每组实际证据的内容

```text
examples/<backend>/<case>/
  input.json             # 实际输入
  scenario.json          # 数据哈希、故障注入、Clock来源、是否fixture_setup
  output.json            # 程序实际最终输出
  plan.md                # 若成功，实际导出方案
  trace.jsonl            # 实际执行事件
  run.json               # 命令、开始/结束时间、退出码、commit、backend、模型参数
```

Trace事件至少含schema_version、event_id、request_id、origin(model/fixture_setup/system)、阶段、动作、参数、公开rationale、观察摘要、结果引用和状态。后续模型动作通过next_decision_event_id关联；最后事件该字段为null。此关联由导出器根据实际事件顺序构建，不事先编造。Token用量记录真实返回值；未知为null；禁止写入密钥、认证头或reasoning_content。

测试结果：`examples/tests/pytest-junit.xml`、`summary.json`；summary保留总数/失败/跳过及pytest退出码。评估文档必须在实现后逐项填写实际路径和结果，不只写“测试通过”。
