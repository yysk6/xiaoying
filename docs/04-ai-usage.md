# AI辅助范围、本人贡献与验证

## 我的协作方式

我使用Codex辅助调研、规格撰写、代码实现、测试、审查和文档整理，业务运行则接入DeepSeek。两者职责分开：Codex是开发工具，交付应用通过普通Python和官方模型API运行，不要求评审安装Codex或接入其内部服务。

我的工作重点是定义问题、明确约束、选择开发路线、审查阶段产出并要求可验证的结果。我没有将“能输出一份方案”直接当成完成，而是继续核对预算、依赖、状态以及模型遇到失败后是否调整动作。实现与测试由AI大量辅助生成；下面按可追溯的设计判断与反馈说明个人贡献，不把AI生成部分标成独立手写。

## AI具体提供了什么

| 类别 | 辅助范围 | 我要求的约束与验证 |
|---|---|---|
| 调研与设计 | 框架对比、模块边界、工具契约、状态/缓存/恢复方案 | 回到题目要求，解释取舍，不因框架名称增加无关能力 |
| 代码与提示 | 领域、工具、SQLite、图、HTTP适配、CLI、需求抽取及版本化提示 | 规格先行、公开依赖、最小充分实现、模型与程序分工 |
| 测试与调试 | 行为测试、故障注入、Schema检查、独立评测器和诊断 | 离线测试禁网络；真实存储不能Mock掉；反例要能让检查器变红 |
| 审查 | 按Spec和Standards两个方向检查变更，提出修订 | 两类发现分开记录，修订后实际复核，未运行不写通过 |
| 评测与交付 | 操作真实DeepSeek运行、提取观察/Trace、汇总及文档 | 固定案例预期、保留失败、注明夹具和E2E边界，不只报告最终状态 |

开发用公开技能主要用于最小改动、TDD、诊断、代码审查和上下文交接；来源/版本与项目适配见[下文技能说明](#开发方法与技能使用)。它们是开发方法，不是应用依赖；业务是单Agent，不因开发时审查子代理而变成多Agent系统。

## 开发方法与技能使用

开发流程为规格/契约先行，按已授权业务行为做可变红的测试、最小实现、自验与审查，再交付；按阶段约束范围，显式连续授权可顺序执行多个阶段。接口/框架设计有具体问题时再做比较，不为未来能力提前抽象。Mock、持久化/恢复、真实模型、平台安装分别验证，不相互代替。

| 公开技能 | 项目用途与实际用法 |
|---|---|
| karpathy-guidelines | 明确假设、最小充分实现、可验证结果；收敛无关框架和重复工作 |
| tdd（含tests/mocking） | 使用公开入口；先真实Red，再最小Green；外部模型/Clock可替换，存储规格用真实SQLite |
| code-review | 业务阶段按Spec与Standards并行复核，记录初始/修复/未解决项，覆盖未提交与未跟踪代码 |
| diagnosing-bugs | 已观察缺陷先建可复现反馈，比较假设、缩小原因；原文依据拒绝/保存观察误报均有实际记录 |
| codebase-design | 具体模块边界/接口问题才使用，集中行为、小接口，优先普通函数 |
| writing-for-agents / handoff | 当前事实与指针去重；根HANDOFF记录目标、边界、证据及下一步，代码运行不读取开发交接 |

六项中文技能的公开来源固定在[vinvcn/mattpocock-skills-zh-CN的5b577186提交](https://github.com/vinvcn/mattpocock-skills-zh-CN/tree/5b57718666917f8a6a0ff3066ae8d5ec386baef4)，18文件安装校验见[原始安装材料](../examples/tests/tooling/skills-installation.json)。karpathy-guidelines另行使用。安装成功不等于技能已执行；未运行的复核不写通过。技能是Markdown方法指引，不进入应用/依赖锁；开发时的审查子代理不使业务变成多Agent。

本人指出流程过碎后，保留必要行为测试与审查，减少缺模块/方法的独立轮次、逐轮重复日志、提前wheel验证和多处维护同一状态。最终代码固定后只做受影响检查；纯文档更动核对链接/差异，必要评测工具适配才加聚焦离线测试。实际执行规则集中在[AGENTS](../AGENTS.md)，不另设技能/开发计划文档。

## 如何约束与验证AI产出

我采用“先明确边界→让AI分阶段实现→用证据检查→反馈修订”的方式。验收口径先于效果运行确定，避免看到结果后修改答案。预算和真实状态由确定性程序保证，模型只提出动作；错误结果仍进入下一轮，让模型决定重试、改方案或停止。

CORE20检查器首审发现三个假通过入口：省略执行步骤、篡改数据库预算、清空成功结果观察。AI先通过变造证据复现失败，再补独立核验、运行测试并复核。这说明评测器也需要检验，不能以AI判断“通过”代替实际证据。详见[审查与修订](03-evaluation.md#spec)。

当前结果为20个核心场景通过、最终完整离线408项通过。真实运行中两次多动作协议错误和持续失败场景的多余请求仍保留；首次强杀恢复异常的后续完整复测已经通过。结果和限制见[评估](03-evaluation.md)。

## 贡献与记录边界

没有单独的个人手写代码diff或人工独立执行清单，不编造这类贡献；本人贡献以上述真实的需求、取舍、过程纠偏、使用反馈与验收要求呈现。代码、提示、测试和本文本身均有AI辅助，最终项目由本人提交并承担理解与解释责任。

实际开发分多次会话推进，未连续记录各项人工投入时间，不由测试时长倒推“总开发用时”或宣称提升百分比。可核对的是运行时间：CORE20运行汇总记录开始/结束和每例耗时，本次交付全量复测154.19秒；这些是执行耗时，不是个人开发工时。

## 数据与密钥

业务资料全部合成，示例配置仅占位符。结构化CLI从环境变量取密钥；交互/专项评测按明确要求用隐藏终端输入，仅进程内存持有。仓库、提示、Trace、错误和文档不保存密钥、认证头或内部推理。开发工具的聊天记录不作为运行时输入，也不随项目提交。
